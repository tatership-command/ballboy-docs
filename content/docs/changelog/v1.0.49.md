# v1.0.49 — Advance Reliability, Rollback Reversal & YouTube Go-Live

_Released 2026-08-03_

## What's New

**🛡️ Ball Boy checks it can actually post before advancing**
Advancing a week creates game threads and posts the weekly announcement. If Ball Boy was missing a permission somewhere in that chain, it used to find out halfway through — after threads already existed.

Now `/season advance` and `/season prepare_week` check first. If Ball Boy can't post in your announcements channel, or can't create threads in your game-thread channel, it stops before creating anything and tells you exactly which permission is missing and in which channel.

The check looks at **channel-level** permissions, not just the bot's server-wide role — which matters, because the usual cause is a channel-specific override denying something the bot's role otherwise grants. If the check can't reach a definite answer (an API hiccup, a channel it can't read), it proceeds rather than blocking you; it only stops when it has positive proof of a missing permission.

**📺 YouTube go-live detection**
Ball Boy now detects when you go live on YouTube and announces it, the same way it already did for Twitch. Link your YouTube channel in the claim window, and announcements fire automatically when you start a stream with an unplayed game for the current week.

One related change under the hood: Twitch detection no longer relies on your Discord "Streaming" status. It uses Twitch's own notifications, which is more reliable and doesn't depend on Discord noticing your status change. In-Discord screen-share detection (from v1.0.48) is unaffected.

**↩️ `/season rollback` properly puts things back**
Rolling a season back now reverses the Discord-side state it left behind, rather than only moving the season pointer. Game threads and announcements from the week you're leaving are handled instead of stranded.

Rollback restores the season's **position** — which week is live, which threads are open, which announcement is current. It deliberately does not rewrite the **record** of what happened: results you reported stay reported.

If you roll back across a CFP bowl week, Ball Boy now warns you that bracket progression isn't automatically recomputed, so you know to check it rather than assuming it sorted itself out.

## Fixes

**🧵 A failed announcement no longer orphans every game thread**
This is the big one, and it came out of a real incident.

When a week advanced, Ball Boy created all the game threads and then posted the weekly announcement. If that final announcement post failed — most often a missing permission in the announcements channel — the entire advance was treated as failed and **none of the thread IDs were saved**, even though every thread had already been created in Discord.

The threads were real and visible, but Ball Boy no longer knew about them. Retrying created a whole fresh set. In the incident that surfaced this, one week ended up with 70 threads for 24 games across three attempts.

Now a failed announcement is just a failed announcement. The threads are kept, the week advances, and you get a warning telling you the announcement didn't post and in which channel. The permission preflight above should stop you reaching this at all — but if you do, the damage is one missing message instead of a channel full of duplicate threads.

**🔕 Auto-advance no longer double-pings the league**
When you advanced by pinging the league (the `@everyone` or announce-role trigger), Ball Boy's weekly announcement pinged everyone a second time, moments after your own message already had.

This affected any league that had never run `/admin auto_advance` — which was most of them, because Ball Boy writes part of that setting itself the first time a season advances, and the old check misread that as "an operator configured this."

A trigger-driven advance is now silent: your trigger message is the notification. You'll see your own ping followed by an unpinned announcement — that's intentional. Advancing with `/season advance` instead still pings normally, since nothing else notified anyone in that case.

**📋 `/season prepare_week` reports what it actually did**
The reply always said "(0 threads)" no matter how many it created, because the message was built before the work ran. It now reports the real count — and if the announcement failed to post, it says so instead of reporting success.
